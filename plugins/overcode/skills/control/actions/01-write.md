# Write

Decide whether a requested test should exist, at which tier, and within budget - before any test code is written.

## Inputs

- `behavior` (required) - one-line description of the behavior or code path that needs coverage
- `project_path` (required) - absolute path to the target project root
- `phase` (optional) - overrides the resolved project phase for this run only
- `domain` (optional) - the declared domain `behavior` belongs to. This action takes **no `scope`**: it judges one behaviour, so there is no universe of files to bound structurally. `domain` is different - it designates no universe either, but it names the **column** of the `phase x domain-level` matrix cell this behaviour falls in (`@../references/decision-matrix.md`). Without it, and absent a pivot **Domain resolution** match, the behaviour is judged in the **out-of-domain** column. **One name, not a list** - given `domain=auth,payment`, stop and ask which was meant: this action parses no multi-valued `domain`, and a behaviour cannot fall in two matrix columns at once.

## Outputs

```
tier: contract | e2e | skip
phase: <resolved phase, one of scaffolding | hardening | production | sustaining | default | undetermined>
       (provenance: argument | declared <path> | answered | unanswered)
domain: <name or out-of-domain> (level: critical | structuring | ordinary | out-of-domain, provenance: argument | resolved <path> | testing-domains.md | catalogue | answered - the last two not persisted)
cell: { required_proof: <anchored | anchored+internal | anchored nominal+degraded | internal | internal on regression | none>, ceiling: <n or none>, established: <n, one count per required term on a conjunctive cell - `2 (anchored: 0, internal: 2)` - or `unknown` when the tests could not be read>, status: ok | at ceiling (n/n) | ceiling not evaluated (established unknown) }
authority: project doc <path> | generic default (references/decision-matrix.md)
rationale: <one paragraph, citing the phase and the cell as context - never as a decision taken outside step 3>
budget_check: { current_count: <n>, limit: <n or null>, status: ok | warn | blocked }
density: { target_file: <path>, value: <ratio>, median: <ratio>, status: ok | outlier (<n>x median) | insufficient population | not applicable }
tooling: { required: contract runner | anchored/E2E runner | none, status: available | unavailable | not applicable, evidence: <wired command or missing capability>, routed_to: 03-configure | none }
delegated_to: aidd-dev:06-test#01-test | aidd-dev:06-test#02-test-journey | none
```

## Process

1. Resolve `project_path`. Look for a documented test strategy at the exact-case path `<project_path>/aidd_docs/memory/testing.md` (the AIDD memory convention), using `SKILL.md` › *The conventional strategy path is exact-case*. Where it is present **and actually settles a tier**, use what it states about tier and ceiling. Otherwise load `@../references/decision-matrix.md` as the generic default for both, and **name which of the three fallback shapes was met** (`SKILL.md` › *Transversal rules*): absent, present but empty, or present and filled while settling no tier. A differently-cased sibling such as `TESTING.md` is reported as a non-canonical candidate and still produces the same `absent` fallback on every OS; it is never discovered merely because the host folds case. The third shape is the trap everywhere, and it is worst here - **this is the only action that decides a tier**, so a document naming test types, tools and conventions credited as an authority in force would attribute to the project a classification it never took. Presence is not the test; settling a tier is. Name the shape, then apply the fallback.
1-bis. Resolve the project **phase** per `@../references/phase-framework.md`, at the same rank as the documented strategy and the pivot: it is loaded context, not a decision input on its own. It is **never deduced** - it comes from the `phase` argument, from the project's own documentation, or from asking the user before the classification is stated. Under `default` and `undetermined` there is nothing to cite as context; say so in `rationale` rather than citing a neutral weighting as if it were a reading of the project - and distinguish the two, since one is a decision the project took and the other a question it has not answered.
1-ter. Resolve the domain **level**. If `domain` names a domain confirmed in `<project_path>/aidd_docs/memory/testing-domains.md` (`06-align`'s output), use its level. If `domain` is named but absent from that file, it is **residue**, and what is settled is its **level, never its name** - the argument is the user's declaration of the name, so asking for it back would confirm the same thing twice. Consult `@../references/domain-catalogue.md` first: when the name matches an entry there, **take that entry's default level without a question**, cite the catalogue as its source in `provenance`, and leave it overridable like any reported value; when it matches nothing, **ask open** - never guess, since guessing would pick a ceiling in the project's place. **That question is put before any tier, cell or ceiling is stated**, on the same ordering 1-bis puts on the phase and for the same reason: the level is the column the cell is read at, so a classification announced first and re-derived after is a classification the user has already read against the wrong column. Either way the level is **not persisted** here, this invocation only, and the output says so and points to `06-align` to freeze it (`SKILL.md` › *Transversal rules*, same words there and in `04-strengthen`). If no `domain` is given and no pivot **Domain resolution** match applies, the behaviour falls in the **out-of-domain** column - never guessed toward a level to save the question.
2. Detect the language plugins applicable to `project_path` - **a set, not a winner** - and check which of them ship a `testing` capability pivot per `@../references/pivot-contract.md`. Load each one that does, and attribute its mechanics to its own stack: the contract's *the pivot follows the file* rule applies here as everywhere, so a project with two stacks states two sets of mechanics rather than electing one. Load for tooling-specific mechanics: test runner, test-count command, the **Anchor boundary** field (refines only the *position* of the anchored/internal boundary in this stack's own terms, never the requirement itself), and *Risk signals* (stack knowledge reported alongside the cell, never a classifying input of its own). For a stack whose plugin ships none, proceed without it and note the gap **naming that stack** - a gap stated of the project reads as though nothing was refined.
3. Read the `phase x domain-level` matrix cell at the phase and level resolved above - the project's own documented strategy if it states one for that cell, else `@../references/decision-matrix.md`. The cell states a **required proof** (or none, on a `—` cell) and a **ceiling**: a count of proofs already established in that required form, never a count of files or test cases. Classify `behavior` into `contract`, `e2e`, or `skip` per the cell's required proof and the deciding order in `decision-matrix.md`. **The tier is that cell's output name - it is not decided on its own.** A non-empty cell requiring anchored proof maps to `e2e` even when an internal seam exists; intrinsic provability is consulted only on a `—` cell. The phase and the domain-level are cited in `rationale` as what the cell was read at; neither moves a `contract` to an `e2e` or the reverse outside of what the cell's required proof states.

   Name the source in `authority`: the project's own strategy where it states that cell, else the matrix. The cascade is applied at every run; a run that applies it without saying which end it landed on leaves the model unauditable, which is why the line is in the output rather than in the prose.

   **Any `—` cell has its permissive regime announced in as many words**, rather than letting an empty `required_proof` imply it. An arbitration nobody states cannot be told apart from one that never happened - and the matrix has fourteen empty cells, of which the `default` and `undetermined` rows are eight: scoping the announcement to those two rows would leave the six others (`scaffolding` × structuring / ordinary / out-of-domain, `hardening` × ordinary / out-of-domain, `production` × out-of-domain) permissive in silence. Under `default` and `undetermined` the announcement carries one thing more - **which of the two** the row was read at, since one is a decision the project took and the other a question it has not answered.

   **The out-of-domain column is stated in as many words too, and on its own ground - never because its cell happens to be `—`.** The two obligations coincide at `scaffolding`, `hardening` and `production`, where that column is empty, and they part company at `sustaining` × out-of-domain, the one cell of the column carrying a real requirement (`internal on regression, 1`): a behaviour judged there against a ceiling, with nobody told which column it was judged in, carries a refusal the user cannot locate. So say the behaviour fell outside every domain in force, and say **what put it there** - no `domain` argument at all, or a `domain` whose resolution matched nothing. `05-stats` carries the same obligation for its own block; this is the sink's half of it.

   **Compare `established` against the ceiling here, not later**, `established` being obtained per `@../references/decision-matrix.md` › *Counting what is established* - one reading of the tests, per required term, never a count of files or cases. When it has reached the ceiling **and every required term is satisfied**, the cell is at ceiling, `status` says `at ceiling (n/n)`, and the output name is `skip` on that ground alone - step 5 then reports it under its own cause. A ceiling that is only read at delegation time is a ceiling the classification never saw.

   **An `established` that could not be obtained is `unknown`, and no ceiling applies to it.** `status` says `ceiling not evaluated`, the classification proceeds on the deciding order alone, and the run states what stopped the reading. `0` and `unknown` are opposite statements and rendering the second as the first would refuse - or license - on a measurement nobody performed.
3-bis. **What no test can prove, and the ceiling that follows.** Before any delegation, separate the part of `behavior` the suite can settle from the part it cannot. A behavior whose truth depends on a **third party still honouring its contract** - that the remote inbox accepts the payload, that the vendor's schema has not moved, that the provider is up - is **out of reach of testing**, whatever tier the cell assigns it. Say so, name **monitoring** as what covers it, and never delegate a test for it: a test written against a live external boundary passes for reasons the project does not control and fails for reasons it cannot fix, so it reports the vendor's weather, not the code's health. **The same rule is in `04-strengthen.md` (*Process*, **External contract dependency**, *Cost cap, per boundary*), and that file is where it is stated in full** - this action holds the identical cap and does not restate its terms, because `SKILL.md` › *Action chaining* makes this action the sink every new test enters through: a ceiling that exists only in the ranking action is a ceiling with a door next to it, and a ceiling restated in two sets of words is two ceilings.

   **Read the cap there and apply it as written; its terms are not repeated here.** What belongs to this action is what the cap does to *this* output, and that is two things and no third. **Reclassify nothing on it**: the tier stays what step 3 decided, and what the cap changes is whether the delegation happens at all - a boundary the cap leaves at zero test is reported as *monitored outside the test suite*, with the tier step 3 named still standing beside it. And when `behavior` asks for more than the cap allows on a single boundary, **say what the extra cases would and would not prove, and let the user decide before step 6 or 7 runs** - the cap refuses an addition, it never removes the user's ability to force one.

3-ter. **Verify that the selected proof can be produced before delegating it.** This check observes tooling; it never reclassifies the cell. A `contract` output requires an installed and wired runner for the behavior's stack. An `e2e` output requires an established mechanism that crosses the stack's real anchor (browser, deployed HTTP boundary, real CLI, or public API as applicable), not a local double that the pivot's **Anchor boundary** calls internal. Record the concrete command or configuration as `available`. If the mechanism is absent, keep `tier`, `cell.required_proof`, and its unmet count unchanged, set `tooling.status: unavailable`, name the missing capability, set `delegated_to: none`, and route the configuration case to `03-configure`. Never invent a runner, silently downgrade anchored proof to internal proof, or delegate a test that the project cannot execute. The route is followed immediately only when the user asked for the full chain or confirms it; otherwise it is reported and this action stops, per `SKILL.md` › *Action chaining*.

4. **Two constraints, never merged - and 3-bis's external-boundary cap is neither of them.** That cap is `04-strengthen`'s, stated there and only applied here; it bounds the test count of **one boundary**, where these two bound a cell and a project. Naming it as a third here would put three numbers in one paragraph with no precedence between them; leaving it unnamed would make the word *two* read as a complete inventory. The **cell ceiling** was already read at step 3 and reported in `cell` - it is in force regardless of any project declaration, from `decision-matrix.md` or the project's own override for that cell. The **project cap** (`budget_check`/`limit`) is a different thing entirely: a numeric budget on the project's *total* test count, populated exclusively from the project's own documented test strategy - never from an internal default invented by this skill. Get the current test count via the pivot's test-count command if available, else count matching test files manually. If the strategy doc states a budget, compare against it and set `limit` accordingly; otherwise `limit` stays `null` and the only check is a subjective warn once the count is unusually large for the project's size, asking the user to confirm before proceeding. State the phase alongside `budget_check`: the phase does not set `limit` - nothing but the project's own document does - but it is what makes a `warn` readable, since the same count means something different in `scaffolding` and in `sustaining`.
4-bis. **Density** per `@../references/test-density.md` - the constraint that applies when no cap is declared, and the one that says something even when a cap is. Compute the project's distribution from its coverage report, take its median, and place the file this test would land on. Report `density` in the output block, and when the file already sits past 3× the median, **say it before delegating** - a new case on a file already saturated is the moment where saying so is still cheap. Then delegate anyway if the tier says so: **density never refuses, and it never changes the tier.** It is the same boundary the phase has, and it is why `tier` is decided at step 3, before this step runs at all. When the project has too few tested files for a median, report `insufficient population` and move on without an outlier - that is the normal state of a `scaffolding` project, not a finding.
5. If `tier = skip`: two distinct causes, reported differently.
   - **Ordinary output name** (already exercised by an existing proof, or a framework pass-through with no branching): report the rationale and stop. Set `delegated_to: none`.

   **An empty `—` cell is not one of those causes.** It states that the phase requires no proof at that level - it never states that a proof is unwelcome. Refusing an addition *because nothing is required* would make an absence of requirement act as a refusal, which is the one thing `decision-matrix.md` denies it (*The matrix*, the paragraph reading a `—` cell). On a `—` cell, classify by the deciding order (`decision-matrix.md`, *Deciding among them*) exactly as anywhere else, report `required_proof: none, ceiling: none`, and delegate normally. **What turns a case into `skip` is a ceiling, never an empty cell** - and a `—` cell has no ceiling to reach.
   - **Cell at ceiling**: report the rationale with motif `at ceiling (n/n) - <phase> x <level>`, and offer **three outcomes**, never a hard block: declare the next phase; remove a test from the domain; force the addition through an explicit, tracked decision that overrides the refusal. **The ceiling refuses an addition, it never requires a removal** - refusing only tightens, requiring would decide in the project's place. Set `delegated_to: none`.

     **A forced addition is not a `skip` that delegates - it is no longer a `skip` at all.** The override removes the one cause that produced the name (`@../references/decision-matrix.md` › *Output names*, third cause), so the behaviour is re-read on the deciding order alone and comes out `contract` or `e2e`, which is what step 6 or 7 then delegates. `tier` carries that name, `cell.status` still says `at ceiling (n/n)`, and `rationale` records the override as an explicit decision of the user's. Emitting `tier: skip` beside a delegation would put a refusal and its own bypass in one output block, and no reader could say which of the two the run actually did.
6. If `tier = contract` **and `tooling.status = available`**: delegate to `aidd-dev:06-test` action `01-test`, passing `behavior` and the tier's quality constraints as explicit input.
7. If `tier = e2e` **and `tooling.status = available`**: delegate to `aidd-dev:06-test` action `02-test-journey`, passing `behavior`.
8. Report the full outcome block to the user before the delegated action starts executing - the user can override the tier or cancel before delegation happens.

## Test

**Referred by file, never by row number.** A row list goes stale on the next renumbering of a suite, and a stale list is worse than none - it points a reader at a scenario that now tests something else. Each suite below declares the actions it targets in its own opening paragraph; that declaration is the authority for this list, and it is the thing to re-read when a suite is added or re-scoped.

Covered by `../evals/authority-scenarios.md`, `../evals/matrix-scenarios.md` and `../evals/chaining-scenarios.md`.

`matrix-scenarios.md` owns what the cell requires and what its ceiling number is; `authority-scenarios.md` owns the bound that the instrument measuring may not decide; `chaining-scenarios.md` owns this action's position in the graph.

**A suite that exercises this action without declaring it is a defect in that suite's declaration, and it is fixed there - never by adding the file to this list.** The list follows the declarations; patching it directly would make the rule above self-confirming and hide the real gap. Two such cases stand at the time of writing: `../evals/measurement-scenarios.md` reaches the external-boundary cap at this sink while declaring `04-strengthen` / `05-stats` only, and `../evals/confirmations-scenarios.md` reaches the addition batch's margin here while declaring `02-audit` / `03-configure` / `04-strengthen` / `06-align`. Both are named here as known gaps to close in those files, not as entries of this list.

Run: `overcode:behave 02-run <suite> <fixture>`.
