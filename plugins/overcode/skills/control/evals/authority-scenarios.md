Behavioural tests for **overcode:control** (`plugins/overcode/skills/control/SKILL.md`, actions `01-write` / `02-audit` / `03-configure` / `04-strengthen` / `05-stats`) — `03-configure` was missing from this list until run 7 although **S13 has exercised it since the suite was written**, and this paragraph is the authority the action files' `## Test` footers resolve against: an action absent from it reads as covered by no suite, which is the one thing a footer referring by file cannot catch — verifies the bound that survives the model's inversion: **the phase decides, and nothing that measures may decide with it**. The decisive properties: a removal is qualified by a *removal heuristic* and never by a phase, a domain or a density; a density outlier signals and never changes a requirement; a domain designates a **column** and never a required proof nor an exclusion; the pivot's *Risk signals* order and never classify; the pivot's *Anchor boundary* says **where** the boundary falls and never **which** proof is required; the **ceiling is explicitly not covered by this bound** — it is an arithmetic of the phase and it *does* refuse; every output name carries **the cell that produced it**, without which the model is unauditable; an **established** e2e runner is never proposed for replacement, a tool being a project decision and not a wiring defect; and `control` writes only what it measured, proposing strategy without applying it.

This suite is **distinct** from:
- `matrix-scenarios.md` — what a cell requires and what the ceiling refuses.
- `phase-scenarios.md` — how a phase is resolved, reported, and switched.
- `domains-scenarios.md` — who declares domains and how an unmatched term is reported.
- `measurement-scenarios.md` — how density, coverage and percentages are computed and read.
- **this file** — who is *forbidden* to decide, and what every measuring mechanism may do instead.

## How to run

Agent-as-`overcode:control` (dry-run, READ-ONLY on the fixture): for each scenario, load **only** the files listed in its *Judge load path* column, plus this suite. Reason out what the skill **would** do — its response AND the precise set of files it would write or modify (paths + scope) — and judge against the pass criteria. Nothing is written to the fixture.

**The bounded load path is the test, not a convenience.** A judge that reads `docs/control.md` or a sibling reference will "know" a rule and score PASS on knowledge the skill, as an agent would actually load it, never had. Loading beyond the declared path invalidates the scenario.

**What the bounding does not do is manufacture ignorance.** Run 8 established that S7's own path restates, twice, the very bound the row was written to isolate (`SKILL.md:78`, `01-write.md:32`). A row whose criterion turns on a rule's **location** must therefore name the file it is scored against and say that a restatement elsewhere does not settle it — the path controls what a compliant run *would see*, it is not a blindfold. A criterion phrased *« otherwise the judge cannot know it »* is a criterion that has not checked its own path.

**Cold judging.** This suite's `## Results log` shares a file with the table, so an unbounded `Read` hands the judge every prior verdict and turns a fresh scoring into a confirmation of the last one. Load the bounded criteria view with `node tools/eval/control-authority-criteria.mjs --print`; it stops structurally before the results marker and its self-check fails if a dated run or tally leaks through. A judge must state that this view was used. Direct offset reads remain valid only when they stop before `## Results log`; never hard-code a line number, because the header grows with every rewrite.

**Friction.** A correct act reached for the wrong motive is a **friction**: the verdict cell reads `FAIL` and the note says so. Friction is never a PASS. S13 names the concrete case for this suite (a fix-free finding), but the settlement applies to any scenario: citing the right rule for the wrong reason does not earn a PASS.

**Density is not measurable on any of the three fixtures.** S3, S10 and S12 are declared N/A above for that cause; none of the three is ever scored PASS on this fixture set, and they stay as written so a fixture that later carries branch data can exercise them without a rewrite. Adding the JS fixture did **not** change this — it has no coverage tooling at all — and a run reporting otherwise has read a figure nothing produced.

**Which fixture a row runs on is part of the row, not a judge's choice.** Three rows now run on `choix-narratifs` (S6, S17) or read the `sc-js` pivot as a document (S15); the rest run on `app` or `ai-hub`. Playing S6 or S17 against a Python fixture makes them unscoreable — the pivot they read is not applicable there — and playing an `app` row against the JS fixture loses the state that row was written for. **Do not migrate a row to the new fixture because it would go green there.**

**S2 and S12 are Δ-scored and cannot be decided by a single run** (S12 remains N/A here regardless, per the note above; the Δ-scoring instruction stands for the fixture that eventually exercises it). Record both runs, then score what changed against what must not have: in S2 the ceiling and the order move while no requirement traces to a risk criterion; in S12 nothing should move at all.

**S14 is the bound's own exception and is the easiest row to get wrong in both directions.** Score the *reason* the run gives, not only whether it refused: a refusal on the ceiling is correct, a refusal on a density is the same word for the opposite defect.

**The `Page rule pinned` column is for the maintainer, not for the judge** — it records which rule of `docs/control.md` a row protects, so a page edit can find its scenarios. The judge never loads the page; doing so would let it "know" a rule the skill does not carry.

**Decisive observables** (write-scoped):

- **No requirement traceable to an instrument.** Every required proof and every ceiling cites its cell; a density, a risk criterion or a pivot field named as the source is an automatic FAIL.
- **No output name without its cell.** An emitted name with an empty rationale, or one citing the tier table as its cause, is unauditable and is scored a FAIL, not a friction.
- **No file leaves the classifiable universe because of a domain.** The exclusion list has exactly three legitimate sources.
- **`05-stats` intended writes = ∅.** Any intended write from `05-stats` is an automatic FAIL.
- **The ceiling refuses; nothing else does.** A refusal is scored on what it cites.
- **No pivot field names its consumer.** A field's own prose naming the action or skill that reads it is an automatic FAIL (S15).
- **A missing runner never lowers a requirement.** A required proof the fixture has no tooling to establish is reported **unmet**, with the tooling gap named and routed; a run that downgrades the requirement to what the available tooling can reach has let an instrument decide, in the one direction no ceiling licenses (S17).
