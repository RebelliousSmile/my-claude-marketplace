# Control

Sits in front of `aidd-dev:06-test` as a gate: before a new test is written, decides whether it should exist at all and at which tier; separately, audits a project's existing tests for low-value candidates, ranks its uncovered code by risk to say what is worth testing next, checks its test tooling for silent misconfiguration, reports at a glance where the suite stands and which strategy governs it, and closes the loop by proposing that the project's own strategy document be brought back in line with what the project actually does. Every action is generic - a project's own documented test strategy, or a language plugin's `testing` pivot, refines the decision; neither is required for this skill to run.

## Available actions

| #  | Action      | Role                                                                                   | Input                                    |
|----|-------------|-----------------------------------------------------------------------------------------|-------------------------------------------|
| 01 | `write`     | Decide tier (contract / e2e / skip) and budget for a new test request, then delegate    | Behavior description, target project path |
| 02 | `audit`     | Find low-value existing tests (duplicates, trivial, getter/setter-only), propose removal | Target project path                       |
| 03 | `configure` | Detect test-tooling misconfiguration and propose fixes, without swapping tools           | Target project path                       |
| 04 | `strengthen`| Rank missing tests / uncovered code by risk, propose the few that matter, via `01-write` | Target project path                       |
| 05 | `stats`     | Read-only snapshot: what each domain's cell requires against what the suite carries, and which test strategy is actually in force | Target project path |
| 06 | `align`     | Audit the gap between the project's test document and its reality, propose the update    | Target project path                       |

## Default flow

Non-sequential - the router dispatches on user intent. Trigger-to-action mapping:

- "add/write a test for X", "should I test X", "is this worth testing" → `01-write`
- "audit the tests", "find low-value tests", "clean up the test suite", "which tests can I delete" → `02-audit`
- "check the test config", "why isn't coverage failing", "fix the test tooling" → `03-configure`
- "what should I test next", "which tests are missing", "where is my coverage weakest", "what's the riskiest untested code" → `04-strengthen`
- "how many tests do we have", "what's our test strategy", "which strategy is in force", "test suite overview", "where do we stand on tests" → `05-stats`
- "align the test documentation", "is the test strategy still up to date", "declare the project's phase", "the test document no longer matches the project", "update our testing.md" → `06-align`

If the target project path is not given, ask for it before running any action - not one of them can produce a meaningful result without it.

## Action chaining

The routes between actions are an **ownership contract, not an automatic invocation contract**: an action names the next owner rather than doing that action's job itself, and an action that is explicitly handed a case must not recompute what it was handed. A direct action request reports its handoff and stops unless the user asked for the whole chain or confirms continuation. `05-stats` always follows its own stricter output contract: it suggests the next action and stops. A requested end-to-end control workflow may traverse the named edges without re-asking between read-only steps.

```
                        05-stats            entry hub
                     /    |    |    \
                    v     v    v     v
         03-configure  02-audit |  06-align
          (terminal)      ^     |    /  |
                          |     v   v   |
                          +-- 04-strengthen
                                  |      |
                                  v      v
                                  01-write        sink
                                  /       \
                     tooling gap v         v proof available
                         03-configure   aidd-dev:06-test
                          (terminal)      leaves this skill
```

Edge by edge, and nothing else is an edge: `05-stats` routes to the four actions that act; `04-strengthen` refers a **density-saturated** file back to `02-audit` - many cases on little logic, and a real gap still open, which reads as cases aimed at the wrong thing; this is not the cell-at-ceiling case, which routes nowhere and returns to the user (`01-write` step 5); `06-align` mobilises `02-audit`'s motives and re-runs `04-strengthen`'s ranking on a phase switch; `04-strengthen` hands every confirmed gap to `01-write`; `01-write` names `03-configure` when the proof the cell requires has no installed mechanism, otherwise it delegates to `aidd-dev:06-test`.

- **`05-stats` is the entry point.** It reads the situation and routes; it proposes no removal, ranks no gap, writes nothing. When the starting point is unknown, it is the action to run.
- **`01-write` is the sink** - every new test enters through it (the transversal rule below states why), and it is where control leaves this skill for `aidd-dev:06-test`. **`02-audit` has no edge to it**, and that is not an omission: an audit removes, it never originates a test.
- **`02-audit` ↔ `04-strengthen` are the two directions of one judgement**, and `06-align` is the only action that mobilises both at once, on a phase switch, and even then it originates neither: the outgoing motives come from `02-audit`, the incoming ranking from `04-strengthen`.
- **`03-configure` is reachable and terminal.** `05-stats` reaches it for a measured wiring defect; `01-write` reaches it when the selected proof form has no installed mechanism. It answers a question the others do not ask, and its answer feeds none of them.

## Parameters

| Parameter | Actions | What it means there |
|---|---|---|
| `phase` | 01, 02, 04, 05, 06 | The project's phase (`references/phase-framework.md`). Never deduced; resolved and reported with its provenance. |
| `scope` | 02, 04, 05, 06 | **One name, one universe, everywhere: the source code and the tests that match it.** The resolution is **symmetric** - a path landing in the test tree resolves up to the corresponding source, a path landing in the source resolves down to its tests, and the universe is the pair either way. `scope=tests/legacy/` stays expressible, and no action has a universe of its own; what differs between actions is which side of the pair they read, never what the parameter bounds. |
| `domain` | 01, 02, 04, 05, 06 | A functional domain (`auth`, `payment`) - **confirmed by the project or residue, both admissible**; a name the project has not declared is resolved per *Transversal rules*, never dropped to out-of-domain. On 02/04/05/06 it prioritises within the analysed universe; it never removes anything from it. On `01-write` it names no universe at all - it names the **level** (`references/decision-matrix.md`) that places the one behaviour being judged in its `phase x domain-level` cell. **One name, not a list**: no action parses a multi-valued `domain`, and given one (`domain=auth,payment`) an action **stops and asks which was meant** - exactly as for the `scope`+`domain` conflict below, and for the same reason. Splitting it silently would run a matrix column nobody named, and taking the first would pick a level by argument order. |
| `top_n` | 04 | How many ranked gaps to report. Bounds the output, never the analysis. |

`03-configure` takes `project_path` and nothing else - see the rule below. `01-write` takes no `scope`: it judges one behaviour, so there is no universe of files to bound structurally. It does take `domain`, not to weight a universe it does not have, but because without a level the cell the behaviour falls in cannot be read at all - a domain passed here designates a matrix column, never a table to reorder.

`scope` and `domain` are **mutually exclusive**. Given both, the action **stops and says so** rather than applying a precedence: one bounds a file set structurally, the other weights a universe semantically, and a silent winner between the two would produce a result whose universe nobody can name. Ask which one was meant.

## Transversal rules

- **A series, not four modulators.** Domains resolve first - they say what counts here, and at what level. The phase applies second: it reads the `phase x domain-level` matrix cell at that level, which states a required proof and a ceiling (`references/decision-matrix.md`). The tier (`contract` / `e2e` / `skip`) is that cell's **output name**, never a decision taken on its own. Density and the pivot's *Risk signals* prioritise and report inside this series; they decide nothing in it. A line of this skill that appears to give either of them the classifying word is a **defect, not an exception**.
- Cell and configuration decisions are sourced in this order of precedence: (1) the target project's own documented test strategy (conventionally `aidd_docs/memory/testing.md`, per the AIDD memory layout) if present, (2) `references/decision-matrix.md` (this skill's generic default) otherwise. A language plugin's `testing` pivot (`references/pivot-contract.md`) layers stack-specific mechanics on top of whichever source applies. **The instrument that measures cannot decide** is the transversal rule that bounds every field it supplies: what measures reports and prioritises - it never classifies, never refuses, never changes an output name. This covers `05-stats`, the density, **the coverage report** and the pivot's *Risk signals*, and the list is not closed, since the rule is about the **nature** of the instrument, not its name. The coverage report is named rather than left to the open end because it is the instrument most easily mistaken for an authority: it is the only one that produces a number resembling a verdict, and a percentage read as a bar to clear is the exact inversion this rule forbids. Concretely: the pivot's **Anchor boundary** field refines only the **position** where anchored proof turns internal, in this stack's own concrete terms - never the requirement itself; *Risk signals* prioritise without classifying; *Domain resolution* completes a domain without overriding one the project stated about its own code. A pivot's authority is never granted in general - it is granted field by field, and a field with no stated bound has no authority to extend. **The cell's ceiling is not bound by this rule**: it is not a measuring instrument, it is what the phase states outright, having become the classifying authority.
- **A project has as many applicable language plugins as it has stacks, and the pivot follows the file** (`references/pivot-contract.md` › *The pivot follows the file*). There is no dominant stack and no election: every applicable plugin contributes its own pivot, and a field is resolved by the pivot of the stack the file under consideration belongs to. Enumerations are unions and say what they combined; counts, coverage figures and tooling lines are rendered per stack and never summed; a missing pivot is stated **of a stack**, never of the run. A repository whose manifest wires both `vitest run` and `cargo test` is the ordinary case, and electing one of the two answers every field out of a stack most of its files are not written in.
- **The conventional strategy path is exact-case.** Resolve `aidd_docs/memory/testing.md` by enumerating its parent directory and comparing the project-relative spelling byte for byte; never rely on the host filesystem's case folding. A sibling such as `TESTING.md` is reported as a non-canonical candidate, but it does not become the conventional authority: the fallback shape is `absent` on every OS unless the project explicitly names that different file as its strategy elsewhere. This same lookup applies in every action that reads the strategy document.
- **Every action but `03-configure`** resolves the target project's **phase** (`scaffolding` / `hardening` / `production` / `sustaining` / `default` / `undetermined`) per `references/phase-framework.md`, and reports it with its provenance (`argument` / `declared <path>` / `answered` / `unanswered`) - **two distinct lines, never merged**: the value says which phase, the provenance says where it came from, and only one pairing is forced (`unanswered` ⇔ `undetermined`). **The phase is never deduced from the repository**: it comes from an explicit `phase` argument, from a declaration in the project's own documentation, or from a question put to the user *before* anything is ranked or proposed. A repository shows what was built; it does not show whether anyone is using it, which is the one thing the phase turns on. `undetermined` means the question went unanswered, never that a guess fell short; `default` means neutrality was chosen and written down, so the question stops being asked. The phase governs the **analysis strategy** - four things and no more: which criteria weigh, **which files enter the reading of the coverage report**, in which order the result comes out, and - at a phase switch only - the qualification of a batch of now-obsolete tests. It bounds **what enters** a reading, provided it says so; it never changes **what a datum means** once read. And it now **classifies**, through the matrix cell it reads: it states a required proof and a ceiling per domain-level, and that ceiling is what turns a case into `skip`. It still never moves a `contract` to an `e2e` or the reverse on its own reasoning - that comes from the cell's required-proof, not from a preference of the phase's. And it fixes a **ceiling, never a floor**: a floor degenerates into a target the moment it is displayed - something to sit just above - while a ceiling cannot, it can only be met or exceeded. This is distinct from a coverage-percentage floor, which stays forbidden for the reason the *instrument that measures* rule states: coverage is a symptom, never a target, in every phase alike.
- **`03-configure` sits outside the phase model, deliberately.** It checks whether the tooling is wired - a coverage gate declared but invoked by nothing, a threshold its own config silently disables. Those defects are true or false regardless of who uses the product, so the phase would weight nothing and the domains would scope nothing. It therefore takes neither `phase`, nor `domain`, nor `scope`; `05-stats` routes *into* it, and it routes out to nothing.
- The target project may declare **domains** - functional parts of the product (`auth`, `payment`, `checkout`), each carrying a **level** (critical / structuring / ordinary), resolved in code by terms. **A term matches as a literal substring, case-insensitively, and a domain's own name is itself one of its terms** - alongside any path the project declares for it. No regex, no stemming, no synonym expansion: a term not appearing verbatim, modulo case, does not match, and what nothing matches is residue for the user to name rather than a gap to guess at (`references/domain-catalogue.md` › *Resolution terms*, in the same words). **The name counting as a term is the part that cannot be left implicit**: `domain=auth` on a codebase whose package is `fediverse_auth` matches nothing in that catalogue entry's own list, so a rule stated without it resolves a name the user just supplied to nothing at all. **And the surface is named: paths and declared identifiers, never an arbitrary occurrence in a file's body.** Substring alone still leaves the set open - on a real repository `Auth` matches around ten paths and several dozen files if every text occurrence counts, a factor of eight between two readings nothing separates - and the whole point of fixing the rule is that two runs on the same repo resolve the same set. A file that merely *mentions* a term in an import, a comment or a log string does not have its behaviour in that column. `references/domain-catalogue.md` is the **detection floor** - `06-align` proposes candidates from it, and **every action taking `domain` consults it** to resolve a level; it is never an inventory the project is bound by. The project declares *which* domains exist and at what level, the pivot's **Domain resolution** field declares *how* to spot them in this stack, and the two cannot contradict each other because they answer different questions; a pivot completes a domain named without a resolution, and never overrides one the project wrote about its own code. **A domain prioritises; it never restricts.** What no domain matches stays in the analysis, ranks lower, and **is reported together with the term that failed to match it** - a silent false negative would declare a central part of the code out of scope with nobody able to see it, which is the exact failure this skill exists to prevent. When a project declares no domain, it runs in the **out-of-domain** column of the matrix - a column read exactly like the other three, never a fallback carrying a substitute inventory of its own. **And that column classifies a file, not a run**: a file no domain in force matches is read in it whether or not other domains are in force, so a run with two domains and a residue reads three columns and every row names which one it came from. Keying the column to "no domain in force at all" would leave the residue of every other run without a cell to read at all, and a row cannot carry a requirement or a ceiling for a column nobody assigned it. No generic list of "critical journeys" stands in for an absent domain: the catalogue proposes candidates, and only the project's own confirmation makes a domain exist.
- **A named domain the project has not confirmed is residue, and residue is resolved, never dropped.** The rule holds in every action that takes `domain`, not only in `01-write`: a name absent from `testing-domains.md` - or a project having no such file at all - does **not** collapse into the out-of-domain column, because collapsing it would answer a question nobody asked by treating a missing declaration as a declaration of insignificance. **The name is not what is asked - passing it as an argument is already the user's declaration, and asking again would confirm the same thing twice.** What remains open is only its **level**. Consult `references/domain-catalogue.md` first: a name matching an entry there **takes that entry's default level without a question**, cited as coming from the catalogue and overridable on sight like any reported value; a name matching nothing is **asked open** - never guessed, since guessing would pick a ceiling in the project's place. The level so resolved is **not persisted** by the action that read it, and the output says so and points to `06-align` to freeze it. Same rule in `01-write`, `04-strengthen` and `06-align`, in those words: a catalogue hit is a hit, and turning it into a question at one end of the skill and not the other is how two runs on the same argument stop being comparable. Only a run with **no `domain` argument and no pivot *Domain resolution* match** runs out-of-domain - absence of a name, never absence of a confirmation.
- Never delete a test file, apply a config fix, or write a proposed missing test, without a separate, explicit per-item confirmation from the user. **Three acts, one regime**, and the phase changes nothing in it: it re-orders a table as much as it likes, it moves no line across the gate. **Two relaxations exist, and they are not symmetric.**
  - **A batch the user names themselves - always for removals, margin-bounded for additions.** A user may designate a set of their own accord and confirm it en bloc. The asymmetry is not caution, and it does not bite the same way on both sides: **each addition moves the number-constraint arithmetic for the next**, so a batch of additions approved in one breath cannot have been weighed against a constraint the batch itself shifts; a removal only loosens that constraint, and what was approved stays approved. But the two objects an addition moves are not alike. The **density** is the project's own moving median: every addition displaces it, so nothing can be counted against it in advance - and it never refuses anyway. The `phase x domain-level` **ceiling** is a fixed number, and a fixed number can be counted in advance. Hence the form: **an addition batch is admissible as long as it fits entirely within the remaining margin of every cell it touches** - none of its members would then have been approved against a constraint another member pushed it past. Past the margin, rows pass **one at a time** through `01-write`, the constraint re-evaluated between each - the rule degrades on its own as a cell fills, down to line-by-line at saturation. The **total** is announced before the first line either way, lot or not - announcing a total is no way of getting it approved - and the **margin** is announced with it: a batch refused for exceeding it states by how much.
  - **`06-align`'s phase-switch batch**, and only there. A removal may be consented to as a **characterised batch** - one consent covering a set whose *membership* is defined by a **selection criterion** rather than assembled item by item. The reason is worth keeping with the rule: a generated test is rewritten at low cost, so deletion is no longer the irreversible act that per-item confirmation was protecting; what still has to be protected is **knowing what is being deleted**. The criterion says what the set *is*; it does not stand in for what the set *contains*. **The enumeration is shown in full, in the same turn as the question** (`06-align.md`, step 11) - a criterion consented to with the list off-screen is a criterion consented to on trust. Past the volume at which the analysis itself stops being meaningful, demand a narrower `scope` rather than either unrolling or hiding the list - the same saturation bound `04-strengthen` already applies, and it bounds the *analysis*, never the disclosure.
- Every new test enters through `01-write`, whichever action surfaced the need - `04-strengthen` proposes and ranks, but hands each confirmed gap back to `01-write` so the tier decision and the number constraint are applied in exactly one place.
- This skill **never decides** the strategic content of the target project's test strategy document on its own. `aidd_docs/memory/testing.md` is owned by `aidd-context`'s project-memory skill, which generates and syncs it (the skill and action names have changed across `aidd-context` majors - refer to the document, never to a pinned action number). Every action but one only reads it. The exception is `06-align`, and only under its own terms: it writes what it has **measured** under its own authority, and it *proposes* a strategy in full prose that the user validates line by line before a word of it reaches the file. What a project decides to test stays the project's decision; what the skill observed is the skill's to state. **A document that settles no tier is treated as absent for tier decisions** - map unit and integration to `contract`, end-to-end to `e2e`, and say so in the output rather than pretending the project has a strategy. There are **three shapes, and every action naming this fallback says which one it met**, because they call for opposite fixes: *absent* (nothing to read), *present but empty* (the template was never filled), and *present, filled, and settling no tier* - it lists test types, tools and conventions without ever saying what deserves a test. The third is the trap: it reads as a strategy, it is written like one, and it governs nothing. Reporting it as "template-shaped" without qualification sends the project to fill placeholders it already filled.
- **The *project-level* number constraint of this skill is a density, not a count** - `references/test-density.md`. Project-level is the qualifier that matters: it replaces the absolute project-wide cap, and it replaces nothing at cell level, where the ceiling stands. Test cases exercising a file over its branch points, read against the **median of the project's own distribution**, with an outlier reported past 3× that median. It replaces the absolute cap as the default constraint, for the reason a cap could never handle: it distinguishes a suite that is too large from a codebase that is large. An explicit test-count cap declared by the project still wins, as a cap - the project's declared strategy is not overridden by a measurement - and the density is reported alongside it, because a cap says how many and a density says whether they are in the right place. A coverage percentage is neither, and is never read as either: `limit` comes only from an explicit test-count limit.
- Density **prioritises and reports; it never refuses.** A refusal comes from the resolved `phase x domain-level` cell - its required proof and its ceiling - same boundary as the phase. And it is never a target: no action proposes work whose only justification is moving a density toward the median.
- Coverage percentage is a symptom, never a target. No action of this skill proposes work whose only justification is moving a coverage number.
- **No action of this skill produces a percentage at all.** It compares **orders, never shares**: `covered`/`total` rather than a rate, ranks rather than proportions, "past 3× the median" rather than a share of files. Two things are not productions and stay: a figure the project itself declared, quoted **verbatim** and outside the `budget` line, and a figure quoted from a tool's own report as that tool's output.
- `02-audit` and `04-strengthen` are two directions of one judgement, and they answer to a **net balance**: the suite's worth is what it proves per unit of maintenance, not its size in either direction. Neither action is a quota - an audit that finds nothing to remove and a strengthen that finds nothing worth adding are both valid outcomes. `04-strengthen` never proposes a test on a path the user has just had `02-audit` remove, unless the risk picture has demonstrably changed since; when both run in one session, report the net effect on the test count rather than each side in isolation.
- Never propose replacing a project's already-established E2E tool. Only propose fixes to its configuration.
- This skill orchestrates and decides; it never writes test code itself. Once a tier is decided in `write`, the actual test is written by delegating to `aidd-dev:06-test`.
