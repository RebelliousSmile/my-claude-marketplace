# PrestaShop strategy

Field-tested on PrestaShop 9.2 (Docker locally, Alwaysdata shared hosting in production). Read with
[prestashop templates](prestashop-templates.md) when a file must be created or reconciled. Facts
marked *verify* are host-specific: probe them on the target before relying on them.

## Repository shape

- The repository versions **project-owned code only**: tooling at the root, and under the
  PrestaShop root (`prestashop/` or equivalent) only `override/`, the project modules (`modules/sc_*`
  or the project prefix) and the child theme. Core, `vendor/`, stock and marketplace modules,
  the stock theme, media, caches and logs are ignored.
- Use an **allowlist `.gitignore`** (`/*` then `!` entries). `!dir/` re-includes only the entry:
  to keep part of a re-included directory, re-ignore its content (`/dir/*`) and allowlist the
  kept children. Re-ignore module `vendor/` and theme `cache/` under allowlisted paths.
- The core `composer.json` under the PrestaShop root belongs to PrestaShop. It is not the
  project's root facade; never add deployment scripts to it.
- `app/config/parameters.php` holds database credentials, prefix and secrets: it is never
  versioned, never transferred and never regenerated by delivery.

## Local

- Use the official image `prestashop/prestashop:<ps-version>-<edition-version>-classic-<php>-apache`
  (e.g. `9.2.0-6.0-classic-8.5-apache`) and pin the PHP minor to the production site's version.
  Make the tag overridable (`PS_IMAGE_TAG`) instead of editing the file to test another PHP.
- Use the production database engine and major version (e.g. `mariadb:10.11`) with a healthcheck
  (`healthcheck.sh --connect --innodb_initialized`) and `depends_on: condition: service_healthy`;
  without it the auto-install races the database.
- `PS_INSTALL_AUTO=1` installs on first start. Keep `PS_FOLDER_ADMIN=admin`: the 9.2 installer
  renames the folder itself to a random name, and any other value makes it fall back to a
  hard-coded `admin-dev` and fail. Read the generated admin folder name from the PrestaShop root
  after install.
- Bind-mount the PrestaShop root (`./prestashop:/var/www/html`) so project code is editable.
  On Windows, a bind mount from the Windows filesystem makes PrestaShop unusable (admin pages
  exceeding minutes): keep the project inside the WSL filesystem and run Docker from there.
- The entrypoint's final `rm: cannot remove '/var/www/html/install/'` is harmless: the installer
  already removed the folder. Confirm `install/` is absent; never expose it.
- An interrupted auto-install leaves `install.lock` without `app/config/parameters.php`; the
  entrypoint then waits and exits 42 on every start. Remove the lock to retry, from inside the
  container (`docker compose run --rm --no-deps -u root --entrypoint rm prestashop /var/www/html/install.lock`): the file belongs to the
  container user and the host user cannot delete it. Never do this on a populated database.
- Run the console as the web user with enough memory:
  `docker compose exec -u www-data prestashop php -d memory_limit=1G bin/console …`.
- Defaults in the compose file are for local only; real values come from an ignored `.env`, with a
  versioned `.env.example` listing names without secrets.

## Production install (manual, once)

- Install the core once by hand from the official distribution archive of the exact version
  (the edition zip published by PrestaShop for that release), not from the repository.
- Choose a non-default table prefix and record it in project memory: it differs from local and
  breaks any hard-coded `ps_`.
- After install, delete `install/` and rename the admin folder if the installer did not.
- **Never run the installer again on an installed shop**: it drops and recreates the tables.
- A 500 at the installer's post-install step can be a race between a bundled module clearing or
  warming the cache (observed with `ps_checkout`: `Failed opening required …ContextBuilder…`)
  and the installer's next request. Check the tables, the admin login and the front before
  concluding the install failed.

## Host capability profile

Record, per target, in addition to the generic profile of [WordPress synchronization](wordpress-sync.md):

- **CLI PHP version versus site PHP version.** The `php` on the SSH `PATH` may differ from the
  version configured for the site (observed: 8.3 CLI for an 8.5 site). Use the explicit binary of
  the site version (Alwaysdata: `/usr/alwaysdata/php/<x.y>/bin/php`, *verify*).
- **CLI php.ini.** A versioned CLI binary may load no `php.ini` and therefore miss `pdo_mysql` and
  `intl`. Pass the site's generated ini with `-c` (Alwaysdata: `~/admin/config/php/php-<id>.ini`,
  *verify*), then prove `extension_loaded('pdo_mysql')` before any console command.
- **Memory.** 256M is not enough to rebuild the Symfony container; run console commands with
  `-d memory_limit=512M` or more. An out-of-memory `cache:clear` leaves a half-renamed cache.
- **Transport.** `rsync`, `tar`, `composer` presence on the target (*verify*); see delivery below.
- **Database access** from the SSH host (`mysqldump` or PHP PDO with `parameters.php`) for backups.

## Code delivery (`deploy:prod`)

- Surface `code` only: the files tracked under the PrestaShop root at an immutable ref. Never the
  database, `img/`, `upload/`, `download/`, `var/`, `parameters.php` or untracked modules.
- Materialize the tracked tree with `git archive <sha> -- <ps-root>/` into a local temporary
  directory, then transfer it with verified `rsync --checksum --itemize-changes`; a preview
  (`--dry-run --stats`) reports changed files and transferable bytes before mutation. When rsync is
  unavailable, use the manifest fallback of the differential synchronization reference; never pipe
  a complete archive over SSH.
- No deletion by default: `override/` also receives files written by installed modules. Files
  removed from the repository are reported and deleted only through an explicit, confirmed step.
- Refuse a ref whose tree contains `parameters.*`, `.env`, SQL dumps or a module `vendor/`.
- Require the core to be installed on the target (`app/config/parameters.php` present) before
  transfer.
- After transfer, with the site's PHP binary and ini: `composer install --no-dev
  --optimize-autoloader` in each project module that has a `composer.json`, then
  `bin/console cache:clear --env=prod --no-warmup`. Let the next web request warm the cache.
- Module install or upgrade is a separate, explicit operation
  (`bin/console prestashop:module install|upgrade <name>`), never a side effect of the code release.
- Proof: HTTP 200 on the front, the admin login page and the checkout page, and no new
  `CRITICAL`/`ERROR` line in the newest `var/logs/prod-*.log`.

## Recovery

- **Admin 500 after renaming the admin folder or after an out-of-memory cache clear**: the prod
  cache keeps paths to the old folder (`var/cache/prod/admin` resolving to
  `admin/themes/new-theme`, plus a stray `admi_` directory). Remove those cache directories, then
  rebuild through a web request or `cache:clear` with enough memory.
- **Container or route errors after delivery**: clear the prod cache with enough memory before
  investigating code.
- Never reinstall to recover. Restore from a fresh database dump instead.

## Module inventory and cleanup

- A fresh 9.x edition installs partner modules (marketing, MCP, shipping, analytics). Inventory
  them with `bin/console prestashop:module list` or the `<prefix>module` table, and decide per module.
- Check declared dependencies before uninstalling (e.g. `ps_accounts` declares `ps_eventbus`;
  `ps_checkout` relies on `ps_accounts`): keep a payment stack until the payment decision is made.
- Agent-facing modules (`ps_mcp_server`, `ps_mcp_tools`) are useful for local agent testing; keep
  them uninstalled on production unless their exposure and authentication have been reviewed.
  Local agent access goes through STDIO, not the HTTP endpoint: set `PS_MCP_SERVER_STARTED` to
  true, then run a small launcher that boots `AdminKernel` before calling
  `McpService::runStdioServer()`. On 9.x the bundled `src/Server/STDIO/stdio-server.php` only loads
  `config.inc.php`, so `$module->get()` returns null. Put the launcher in `bin/`, which is denied
  over HTTP, and run it with `docker compose exec -T -u www-data prestashop php -d display_errors=stderr bin/<launcher>`:
  stdout must carry JSON-RPC only. The tools include writes (customers, orders, products).
- Back up the database, uninstall locally first (`prestashop:module uninstall <name>`), prove
  front, admin and checkout, then repeat on the target. Uninstalling keeps the module directory.
- Uninstalling a module is a `data` mutation on production: it needs a fresh backup and an explicit
  confirmation like any production data operation.
